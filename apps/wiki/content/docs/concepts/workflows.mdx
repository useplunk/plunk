Workflows are graph-based automations that move contacts through a sequence of steps — sending emails, waiting for activity, branching on conditions, calling webhooks, updating contact data, or exiting. Each contact that enters a workflow runs through it independently as a **workflow execution**.

## Triggers

A workflow has a single **trigger** that decides how contacts enter:

| Trigger type | When it fires                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| `EVENT`      | Any time a matching event is tracked on a contact (custom event via `/v1/track`, system events such as `email.received` or `contact.subscribed`, or segment entry/exit events). |
| `MANUAL`     | Only when you explicitly start an execution via `POST /workflows/:id/executions`.                      |
| `SCHEDULE`   | On a recurring schedule defined by `triggerConfig` (e.g. cron expression).                             |

When you create a workflow via the API, the trigger defaults to `EVENT` with the event name you provide. To use `MANUAL` or `SCHEDULE`, change `triggerType` and `triggerConfig` with `PATCH /workflows/:id` after creation.

A workflow's trigger event name **cannot be changed after the first execution** — pick it carefully. Other trigger configuration (delays, conditions inside steps) remains editable.

## Lifecycle and the `enabled` flag

Workflows are created with `enabled: false`. **No executions start until you flip `enabled` to `true`** — this is the most common reason "my workflow isn't firing."

## Entry rules

Each workflow decides who can enter it when its event fires. In the dashboard this is **Who can enter** in the workflow's settings; through the API it is `allowReentry` and `throttle`.

| Rule                       | API                                   | A contact enters…                                                                     |
| -------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------- |
| Once per contact (default) | `allowReentry: false`                 | One time, ever. Use it for welcome and onboarding sequences.                          |
| Every time the event fires | `allowReentry: true`                  | Again on each event, even while an earlier run is still waiting in a delay.           |
| At most once per period    | `allowReentry: true`, `throttle: "24h"` | At most once per period, and never while an earlier run is still going.             |

### Throttling entry

`throttle` takes the same value as [`delivery.throttle`](/guides/throttling) on `POST /v1/send`, so an event you track from a busy code path starts the workflow at most once per period. Events inside the period are ignored: no run is started and nothing is stored for them.

```json
{ "allowReentry": true, "throttle": "24h" }
{ "allowReentry": true, "throttle": { "window": "24h", "key": "event.orgId" } }
{ "allowReentry": true, "throttle": { "key": "event.period" } }
```

- **`window`**: from 1 minute (`"1m"`) to 365 days (`"365d"`). The period starts when the contact enters, because a run may branch or exit without sending anything.
- **`key`**: a field to count separately for, read like a condition step's field: `event.*` from the event's data, `data.*` from the contact's data. With `event.orgId`, a person in two organisations enters once per period for each. If the field is missing on an event, it counts per contact.
- **A key without a window** enters once per value, for example once per billing period when the event carries `period: "2026-10"`.
- Setting a throttle turns `allowReentry` on. Setting `allowReentry: false` or `throttle: null` removes it.

Starting a throttled workflow manually with `POST /workflows/:id/executions` returns `409` with the time the contact can enter again. Changing the throttle applies to the next entries; contacts already held keep their period.

## Step types

A workflow always begins with a single auto-created `TRIGGER` step. You build the rest of the graph by adding steps and **transitions** (edges) between them.

| Step type         | Purpose                                                                                                | Required config                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| `TRIGGER`         | Auto-created entry point. Holds the trigger configuration.                                             | `eventName` (for `EVENT` trigger)                                |
| `SEND_EMAIL`      | Sends an email to the contact using a template. Template variables resolve from contact data + execution context. | `templateId`, optional `from` override                  |
| `DELAY`           | Pauses the execution for a fixed duration before continuing.                                           | `amount`, `unit` (`minutes` / `hours` / `days`)                  |
| `WAIT_FOR_EVENT`  | Pauses until a specified event is tracked on the contact, with a timeout fallback.                     | `eventName`, `timeout` (seconds; `0` or omitted waits with no limit) |
| `CONDITION`       | Branches the execution based on contact data or event data. Each `CONDITION` step has two outgoing transitions tagged `yes` / `no`. | A filter expression (same shape as segment filters) |
| `WEBHOOK`         | Calls an external HTTPS endpoint with contact + execution context as the JSON body. `url`, header values, and `body` support `{{variables}}`. | `url`, optional `method`, `headers`, `body`            |
| `UPDATE_CONTACT`  | Patches contact data — useful for tagging contacts as they progress (`{ stage: "activated" }`).        | `data` object                                                    |
| `EXIT`            | Terminates the execution. Optionally records an `exitReason` for analytics.                            | optional `reason`                                                |
| `HOLD`            | Ends the workflow without completing it. Contacts wait here with no time limit, and receive steps you later add above it. See [Hold steps](#hold-steps). | none                                     |

## Hold steps

A `HOLD` step is the end of a workflow that keeps growing. Instead of completing, a contact that reaches it waits there, and when you add steps above it later, the contacts already waiting go through them too. It is how you run an "infinite" nurture sequence: write the next email whenever you like, and everyone who reached the end receives it.

- **Optional and repeatable.** Add as many as you need, for example one at the end of each branch of a condition. Nothing can be connected after a hold.
- **Adding steps.** Insert steps on a connection into the hold (the **+** on the connection in the builder, or `POST /workflows/:id/transitions/:transitionId/insert-step`). Contacts who arrived through that connection run the new steps and then wait on the hold again. Contacts who arrived through another branch are not affected.
- **When they move.** Right away, as with any edit to a workflow. A step that is not configured yet (an email with no template, say) is skipped until you save its configuration, and then the contacts move into it. A condition also waits until every one of its branches is connected, so nobody takes a branch that leads nowhere and drops out of the workflow. A disabled workflow moves nobody; enabling it does.
- **Delays above a hold.** A delay looks up the step after it when the wait ends, so contacts waiting in a delay also pick up a step inserted right after it.
- **Deleting a hold.** Contacts waiting on it are marked `COMPLETED` (`exitReason: "Hold step removed"`) in the background before the step is removed. They will not receive steps you add later. The connection that waiting contacts arrived through cannot be deleted while they are there; insert steps on it instead.
- **Re-entry.** With re-entry allowed, a contact keeps one run waiting on a hold: when a newer run of theirs reaches a hold, the older one is completed (`exitReason: "Superseded by a newer run"`), so a step added later reaches them once.

## Transitions

Transitions are the edges of the workflow graph. For most step types a transition is a simple "next" pointer. For `CONDITION` steps, each transition carries a `branch` discriminator (`"yes"` or `"no"`) so the engine knows which path to take when the condition evaluates.

When deleting a step in the middle of a chain, pass `?splice=true` on `DELETE /workflows/:id/steps/:stepId` to automatically reconnect the surrounding transitions; otherwise the deletion leaves the graph disconnected.

## Executions

Each contact entering the workflow creates a `WorkflowExecution`. Executions move through these states:

| Status      | Meaning                                                                                       |
| ----------- | --------------------------------------------------------------------------------------------- |
| `RUNNING`   | Currently processing a step (or about to).                                                    |
| `WAITING`   | Paused inside a `DELAY` or `WAIT_FOR_EVENT` step.                                             |
| `HELD`      | Waiting on a `HOLD` step for steps to be added above it. Does not lock the workflow, and `cancel-all` leaves it alone; cancel it individually or delete the hold. |
| `COMPLETED` | Reached the end of the graph successfully.                                                    |
| `EXITED`    | Hit an `EXIT` step. `exitReason` records why.                                                 |
| `FAILED`    | An unrecoverable error occurred (e.g. webhook returned non-2xx after retries, template not found). |
| `CANCELLED` | Cancelled manually via the API or dashboard. Pending delays and waits do not resume it; a step already running finishes, and an email it queued is still sent. |

Each execution carries a `context` JSON object that's merged with the contact's `data` when rendering templates and evaluating conditions. When you start an execution manually with `POST /workflows/:id/executions`, you can pass an initial `context` — this is how you parameterise per-execution variables (a coupon code, a referrer name) without storing them on the contact.

## Locking active workflows

A workflow is **locked** for structural edits while it has active (`RUNNING` or `WAITING`) executions. To make breaking changes — adding/removing steps, changing the trigger event, switching trigger type — first either:

- Disable the workflow and wait for active executions to complete (an execution waiting on a `WAIT_FOR_EVENT` step with no timeout only completes when its event arrives), or
- `POST /workflows/:id/executions/cancel-all` to cancel everything in flight.

Cosmetic changes (renaming, editing template content referenced by steps) don't require this. A step's configuration can also be changed while the workflow runs, as long as no execution is currently on that step: a step reads its configuration when an execution reaches it. Executions `HELD` on a hold never lock the workflow.

## Common patterns

- **Welcome series** — `EVENT` trigger on `signed_up`, send welcome email, delay 2 days, send tips email, delay 5 days, send upgrade nudge.
- **Inbound auto-reply** — `EVENT` trigger on `email.received`, `CONDITION` on `event.spamVerdict == "PASS"`, then `SEND_EMAIL` with an auto-reply template. See [Receiving emails](/guides/receiving-emails).
- **Re-engagement** — Triggered by a segment exit (`segment.active-users.exit`), send a "we miss you" email, then wait up to 7 days for an `email.open` event (an open of any email counts) before continuing.
- **Infinite nurture** — `EVENT` trigger on `subscribed`, a few emails with delays between them, ending in a `HOLD`. Whenever you write a new email, insert it (and a delay) above the hold; everyone who reached the end receives it.
- **Webhook fan-out** — `EVENT` trigger on `purchase.completed`, `WEBHOOK` step to your CRM, `UPDATE_CONTACT` to tag `{ tier: "customer" }`, `SEND_EMAIL` with the receipt.

## API reference

Workflows are managed through the `/workflows` API. See the [API overview](/api-reference/overview#workflows) for the full route list — the API exposes endpoints for the workflow itself, its steps, its transitions, and its executions.
